# platform-api contract

`ach platform-api`: the REST API, keys, OAuth 2.1 sign-in over Dex, the console, the OpenCode endpoints and the Enterprise observability routes. Read before changing `internal/platformapi/`. Key exchange is in [`key-exchange.md`](key-exchange.md); LiteLLM semantics in [`../litellm-permission-model.md`](../litellm-permission-model.md).

## Keys

REST + `pk_`/`ek_` lifecycle (an `ek_` is minted ONLY into its Environment's deny-all shell team `ach-env-<env>` — no models, no object_permission, no access-group binding; a `pk_` is minted into the caller's per-user deny-all shell team `ach-user-<email>` (provisioned idempotently at mint; a duplicate answer then triggers one drift-repair — `GET /team/info`, and `POST /team/update` only when the team is ACH-owned AND drifted — the user shell's only repair path, since no reconciler owns it; failures are logged, never fatal to the login) with a matching key expiry — grants attach via the operator, not platform-api; see `references/litellm-permission-model.md`; `POST /platform/keys` (ek_ create, optional future-dated `expires_at` else 400 `invalid_argument`, enforced by ACH only — no LiteLLM `duration`; optional `budget: {max_budget, budget_duration?}` capping THAT key through its own `key:<id>` tag, written after the row commits — a refused write is 502 `litellm_rejected`, never a silently uncapped key) + `PATCH /platform/keys/{id}/budget` (owner-scoped like suspend/resume, 400 unless `max_budget` is present and >= 0, 409 on a revoked key, 409 `budget_managed_by_grant` on an exchange key (its KeyGrant owns the ceiling), 204; ~10s to take effect through LiteLLM's tag cache) + `POST /platform/keys/{id}/suspend`/`/resume` (ek_ only, idempotent; suspend `DEL`s the resolver cache entry, ≤60s enforcement bound, which also covers requests already running (re-checked every 60 s, see the forwarder row); resume 409 on revoked/expired, 403 `unauthorized_team` when access is lost) + `DELETE /platform/keys/{id}` (ek_ revoke from any state, idempotent; also caller-scoped pk self-revoke, owner==caller, NOT admin-gated, `?force=true` overrides the active-key 409 guard; a pk_ revoke (self or admin) also ends the owner's OAuth sessions — they must log in again); combined read `GET /platform/keys` (pk_ callers only — an ek_ is 401 `invalid_key_type`, as is an ek_ on the pkid_ revoke branch; five effective states active/suspended/expired/invalid/revoked, priority Revoked→Expired→Suspended→Invalid→Active, `invalid`=owner lost Environment access or the IdP refused the owner (`idp_refusals`), `?status=` filters on the effective state, `reasons` subset of `suspended|expired|no_access|access_unverified|idp_refused`) + `GET /platform/admin/keys` (SQL-level status only, no Invalid derivation, reason `idp_refused` on an IdP-refused owner's ek_, `?status=` also accepts `suspended`)

## Admin and UI objects

Admin is decided once per request in `Authn`, for `pk_` callers only: the
owner email is in `platformApi.admins.users` (`/etc/ach/admins/admins.txt`,
read at start), or Valkey holds `ach:oauth:sso_admin:<email>`. That record is
written at login and rewritten at every IdP revalidation (`/token` refresh,
console revalidation, `POST /platform/refresh`, the idp sweep) from the Dex
`groups` claim against `platformApi.admins.sso` (`ACH_ADMINS_SSO`); groups Dex
could not deliver clear it until the next revalidation. `AdminOnly` and every
handler read `KeyContext.IsAdmin`.

admin object inventory (read) + UI Objects API (write, Environment only — `/platform/objects`) + `PATCH /platform/admin/users/{email}/budget` (admin-gated; sets that person's whole-footprint ceiling on their `user:<email>` tag — same body and rule as the ek_ route, 204, a never-logged-in user is created not refused; durable — a login never overwrites it) + admin runtime catalog read (`GET /platform/admin/runtime/{models,mcp-servers,a2a-agents,teams,catalog}`)

## OAuth 2.1 sign-in

**OAuth 2.1 AS — the only login** (`/platform/oauth/{register,authorize,as-callback,device_authorization,device,token}`: DCR (`/register` answers 413 over 4 KiB, 400 on a bad record, 429 `rate_limited` past a per-address and a global bucket, per replica; https redirect_uris only on `platformApi.oauth.redirectHosts` -> `ACH_OAUTH_REDIRECT_HOSTS`, default: loopback only; enforced at register AND `/authorize`), code+PKCE S256 via Dex, RFC 8628 device grant for headless hosts (`ach-cli login --no-browser`), refresh rotation **re-validated at the IdP** — `offline_access` at Dex, ONE Dex refresh token per user in Valkey (Dex keeps one per user+client and a new login replaces it, so every tool of the user shares and rotates it), every ACH refresh replays it, a Dex 400 (reuse, unknown or expired token) ends all the user's sessions and revokes the oauth `pk_`, while a Dex 500 (a connector failure Dex does not classify as an upstream rejection) and an unreachable Dex are both a 503 and end nothing; a Dex answer of the upstream rejection (`invalid_grant`, "The upstream identity provider rejected the refresh token.") also records the owner in `idp_refusals`, and every `ek_` they own (exchange keys included) stops resolving until they log in again (the login deletes the row); an hourly platform-api sweep replays, at most once per owner per 24 h (Valkey `idp_check` claim), the Dex token of every owner whose `ek_` was used in the last 7 days, so a leaver who never logs in again is caught within a day, whatever IdP Dex fronts, provided the Dex build includes dexidp/dex#5132 (the upstream rejection) and the connector's own fix (dexidp/dex#5142 for `google`, dexidp/dex#5144 for `gitlab`, `microsoft`, `github`, `gitea` and `bitbucketcloud`; neither is in Dex v2.46.1); connectors that never contact the upstream on refresh (`saml`, `oauth`, `keystone`, `authproxy`) cannot, and their offboarding stays `POST /platform/admin/users/{email}/revoke-keys`; an owner with no Dex token in Valkey is only logged ("owner not verifiable at the IdP"); other Dex 400s (reuse, expiry) end sessions but never refuse keys; `revoke-keys` (`ach-cli admin keys revoke --owner`; email normalised, every page walked, 500 if a list page fails, safe to rerun) remains the explicit offboarding step; no `pk_` is minted at login; `provisionUser` SEEDS the chart-configured default ceiling (`platformApi.userDefaults` → `ACH_USER_MAX_BUDGET`/`ACH_USER_BUDGET_DURATION`) onto the caller's `user:<email>` tag at login, but only while that tag carries no budget (one `/tag/info` read first), so an admin's `PATCH /platform/admin/users/{email}/budget` survives later logins and changing the chart default does NOT retune anyone already seeded; both the read and the write are fail-loud AT THE CALLBACK. The same seed also runs from `ensureOAuthPK`, the funnel EVERY grant crosses (login, `/token` refresh, device grant, console revalidation): a user provisioned before the default existed only ever refreshes and would otherwise never be seeded at all. There it is BEST-EFFORT — this path carries token refresh, so failing it on a LiteLLM blip would sign out every active user at once; what is missing is a ceiling, not a credential, and the next grant retries. The no-clobber guard lives inside `upsertUserBudgetTag`, so an admin's ceiling is safe on every call site — one ceiling covers their pk_ and every ek_ they own; issues 1h Ed25519 JWTs signed with the mounted `ach-jwt-signing-keys` seed (`ACH_JWT_SECRET_DIR`, re-read every 30 s so a rotation needs no restart); each user's JWT resolves to one `personal_keys` row with `purpose='oauth'`, re-minted at `/token` when LiteLLM no longer lists its key (one `GET /key/list` per issue); RFC 8414/9728 documents are served by the forwarder)

## OpenCode install manifest

the **OpenCode install manifest** for that AS (`GET /.well-known/opencode`, anonymous, public data only; the gateway routes that exact path to platform-api, the rest of `/.well-known/` stays on the forwarder: `opencode auth login https://<ACH_BASE_URL>` (engines v1 and v2) installs the plugin `genai.opencodePluginSpec` → `ACH_OPENCODE_PLUGIN_SPEC` (default `git+https://github.com/ackstorm/opencode-oidc-provider.git#v<tag>`, empty = unmounted) with options `{api, platform, provider}`, plus `config.enabled_providers: [<provider>, ...genai.opencodeExtraProviders]` (→ `ACH_OPENCODE_EXTRA_PROVIDERS`, comma-separated, same id rule, refused at start otherwise; only those providers in the picker; v1: the user's opencode.json overrides it; v2: it cannot, anomalyco/opencode#59267) — `provider` is `genai.providerName` → `ACH_GENAI_PROVIDER_NAME`, default `ai-platform`; `auth.command` is `echo ok` filler (OpenCode requires an auth block and spawns it shell-less via cross-spawn; the plugin ignores its credential; `/bin/echo` exists on Linux/macOS and cross-spawn runs a non-.exe name through `cmd.exe /c` on Windows — `opencode` itself is often not on PATH); the user then signs in with `opencode auth login <provider>` (v1: `-p <provider>`), browser loopback or the RFC 8628 device grant; ACH ships no plugin code — `github.com/ackstorm/opencode-oidc-provider` owns it (shared with alitellm-auth); `ACH_GENAI_PROVIDER_NAME` must match the plugin's `^[a-z0-9][a-z0-9-]{0,63}$` or platform-api refuses to start)

## Per-user OpenCode config

**per-user OpenCode config** `GET /clients/opencode/config` (outside Authn; schema `ackstorm.opencode-config/1`, shared with alitellm-auth; 200 for ANY Bearer — an ACH OAuth token that does not verify, or whose oauth `pk_` is revoked, gets the empty baseline `auth:"invalid"`; 401 only without a Bearer; never 5xx — a LiteLLM/DB failure serves the user's last good body from Valkey (`opencode_config`, 30 d, `stale:true`); `no-store`. Optional `config.model`/`config.small_model` = `<provider>/<name>` from `genai.defaultModel`/`defaultSmallModel` (`ACH_GENAI_DEFAULT_MODEL`/`_SMALL_MODEL`, bare names, empty = off), emitted ONLY when the name is a key in the user's own model map (else omitted, OpenCode picks the first); never in the static `/.well-known/opencode`; the user's own opencode.json wins (the plugin merges `config` under it); part of `version` via `config`. Models = the user's own chat `/model_group/info` rows, plus those with no mode (absent or `""`; the deployment's mode from `/v2/model/info` decides when LiteLLM knows it — same rule as the forwarder's `/v1/models`) (minus `a2a/<agent>`: LiteLLM lists a granted agent there but refuses it as a model) under provider `genai.providerName`, enriched (never widened) by master-key `/v2/model/info` + `router_settings.model_group_alias`, cached per replica 1 h stale-while-revalidate; NO `mcp` key (the plugin treats a missing `mcp` as none): MCP servers reach OpenCode only through a hydrated Environment (`ach-cli environment hydrate --target opencode`); `skills` = ONE embedded skill named `<provider>-ach` (`internal/platformapi/opencode/skill/SKILL.md`, a single self-contained file — the plugin writes only `files["SKILL.md"]`, ≤256 KB; platform-api refuses to start when `<provider>-ach` breaks the plugin's kebab-case ≤64 rule; the plugin deletes a skill the server stops listing): a minimal bootstrap — install `ach-cli` from the GitHub release, login, `environment list`, hydrate an Environment the user named into the folder, and `genai.defaultEnvironment` → `ACH_GENAI_DEFAULT_ENVIRONMENT` globally (`{{default_env}}`; step cut when empty); everything after that comes from the `ach-cli` plugin that Environment carries (`plugins/ach-cli`), so the default Environment should list `ach-cli@<marketplace>` — update the bootstrap when those commands change)

## Console session

**web console session** (`/platform/console/session/{login,logout}`: the same AS in-process — a `Console` pending, cookie `__Host-ach_console` HttpOnly/Lax, revalidated at the IdP every AccessTTL through the shared Dex refresh token, logout deletes the web session ONLY) + the cookie→`KeyContext` adapter (`middleware.AuthnOptions.Cookie`: same handlers as a bearer; cookie + any API credential = 400 `ambiguous_credentials`; non-safe methods need `Sec-Fetch-Site: same-origin` or `Origin`==host)

## Console bootstrap

`/platform/console/{bootstrap,capabilities}` (bootstrap also carries `budget` for personal (pk) callers only: the caller's `user:<email>` tag as `{spend, max_budget, budget_duration, reset_at}` — `max_budget`/`budget_duration`/`reset_at` null without a ceiling (`reset_at` = LiteLLM's `budget_reset_at`, verbatim; `/stats`'s `budget.reset_at` is the same value; `spend` = the tag's OWN spend over the current cycle (never before the tag's `created_at`) → now, summed from master-key `/tag/daily/activity` across all pages — `/tag/info` carries no spend; the cycle start is one CALENDAR step before `budget_reset_at` (`30d` = a month — LiteLLM's reset grid), rounded to the nearest UTC-day bucket (≤12 h skew); `/stats`'s `budget.current` is the same figure), `spend` null (ceiling still shown) when the cycle spend cannot be read, the whole field null when the tag is absent, the caller is an ek_ (no `/tag/info` call is made — mirrors `/platform/console/stats`, which 401s an ek_), or `/tag/info` fails, never an HTTP error; `ach-cli whoami` prints it (`Budget   unavailable` for an ek_ credential); Personal scope = LiteLLM reads as the user's OWN key via `litellm.UserView`, public projections only, deny-all-only or empty = `provisioning` (both sentinels recognised — `no-default-models`, and `__deny_all__` on shells an older ACH wrote); Environment scope = the projection behind `environments.CallerMayRead`)

## Console stats and latency

`/platform/console/{stats,latency}` (GET, pk_-only — same guard as `capabilities`, 401 `invalid_key_type` for an `ek_`; each folds the caller's OWN LiteLLM window into `observability.{Stats,Latency}Contract` plus a top-level `"data_scope":"user"` always — user-global, never Environment-scoped, and includes traffic sent through any `ek_` the same owner holds; `stats`'s per-key rows relabel an ACH-managed key's alias to its ek_ `name`, or `"personal"` for the pk_ row, and folds every row the owner's OWN key set does not account for (another product's key, a sibling ACH release's, one made by hand in LiteLLM) into a single `external key` row — summed, never dropped, so the block still covers the whole user-global window; ownership is decided by the owner's key rows, not a metadata issuer check, since each release tracks its keys in its own DB; independent degradation — a failed prior-window read only drops `capabilities.deltas` (all `totals.deltas.*` null), a failed `/tag/info` read only degrades `budget.source` to `"unknown"` (the budget panel reports the caller's own `user:<email>` tag — the ceiling the forwarder enforces — read with the MASTER client, `source: "tag"`), a failed CURRENT-window read is a hard 502 `litellm_rejected` (4xx/`Auth401Error`) or 503 `litellm_unreachable` (transport/5xx) — never a master-key retry, §10.1; `latency`'s `/spend/logs/v2` fetch degrades to 200 `{"available":false,"reason":"unavailable"}` on a 401 `role=unknown`, or `"fetch_failed"` on any other error, never an HTTP error)

## Enterprise observability

**personal traces** `GET /platform/observability/traces[/{trace_id}]` (Enterprise: `ee/platformapi/obsapi` over `ee/observability/evidence`, enabled by `enterprise.enabled`; without it every `/platform/observability/*` route answers 403 `enterprise_only` (core serves none); the guard, window and error mapping are `internal/platformapi/obsapi`'s; pk_-only, an ek_ or no key context is 401 `invalid_key_type` before any read; the caller's email comes ONLY from the key context via `evidence.NewUserScope`, never from the request; thin net/http ClickHouse client as the read-only `ach_observability_ro` user (metadata columns, never input/output), `FINAL`+`is_deleted=0` on `events_full`; a trace holding any span of another user is never served; unknown or foreign trace = 404 `trace_not_found` (no oracle), source failure = 503 `not_ready`, never upstream text; dates `YYYY-MM-DD` UTC, default 30 d, max 31 d; `ACH_OBSERVABILITY_CLICKHOUSE_URL` unset = 503 `not_ready`, set = `_USER`, `_PASSWORD` and `ACH_OBSERVABILITY_LANGFUSE_PROJECT_IDS` all required or startup fails; chart `platformApi.observability.{clickhouseUrl,secretName,projectIds,thanosUrl}`) + the same guard and window on the Enterprise `GET /platform/observability/{sessions[/{session_id}],context,workloads,cost,latency,performance,classification}` (`sessions` groups the caller's traces by session, `sessions/{id}` is its turn-and-tool execution; whole-window aggregates of the caller's generations; a measurement no row carries is null with a reason, never 0; `workloads` takes the User-Agent from the trace's unowned gateway span and sums tokens + cost per runtime; `classification` joins the caller's in-window sessions to the classifier's `ach_classification_category` v3 scores in `default.scores` (granted columns only, never `comment`/`string_value`; no grant = unavailable provenance, never a 5xx) and reports per category + `coverage` labelled/sessions; `cost` keeps zero-cost (subscription) generations out of every denominator and prices the cache saving from LiteLLM list prices scaled per model by recorded/list — Vertex `eu` bills `regional_endpoint_uplift_multiplier` 1.1x; `performance` reads LiteLLM gateway series from Thanos by `user=<email>` (`ACH_OBSERVABILITY_THANOS_URL`, Enterprise-only, refused at start while disabled; optional, unset = `not_instrumented`)); `/platform/console/stats` `budget.projection` carries the cycle's spend linearly to `reset_at` (null `no_cycle`/`too_early`/`spend_unknown`) and `budget.cycle_series` (`[{date, spend}]`) the same tag read's per-day rows, summing to `budget.current`

## UI write path

**GitOps-wins UI write path**: the platform-api UI
Objects API (`/platform/objects`, Environment only in v1) also writes
`origin='ui'` draft rows; the operator is always authoritative and TAKES OVER a
matching `ui` row on CR apply (`origin` 'ui'→'cr', `locked=TRUE`), while the UI
is fenced from operator-owned rows (`403 immutable_via_ui`). Round-trip: draft
in UI → `GET …/yaml` export → commit + `kubectl apply` → operator takeover.
The export renders the spec stored verbatim in `environments.spec` (jsonb,
migration 000024 — written by the operator and the UI path), NOT the per-field
columns: those carry the operator's runtime-group expansion and lack e.g.
`budget`; they are rebuilt only for a row older than 000024.

## Per-user key ceiling

Per-user `ek_` key ceiling: `POST /platform/keys` returns 403
`key_limit_reached` once the caller holds `max_keys` non-revoked rows (active,
suspended, or expired; revoked never counts). The ceiling is the Postgres
`user_limits` row for that email, otherwise
`platformApi.userDefaults.maxKeys` → `ACH_USER_MAX_KEYS` (0 = deny by default).
It is read fresh on every create and never seeded at login; admins are not
exempt and grant themselves with `PATCH /platform/admin/users/{email}/limits`.
That admin route accepts `{"max_keys": N}` (N >= 0), upserts the Postgres row,
returns 204, and takes effect on the next create without a cache delay.

## Login team enrolment

Login team enrolment (`platformApi.teams` → `ACH_TEAMS_DEFAULT`/`_USER`/`_SSO`, JSON):
at every interactive login (`as-callback` — CLI loopback, device grant, console;
never token refresh) `provisionUser` adds the USER (never a key) to LiteLLM teams
by alias. `default` teams (chart default `[default]`, ≥1 required at start) are
mandatory — a missing one fails the login (`default_team_missing`; the operator self-bootstraps only the alias `default`, any other default team must already exist). `users`
(email → teams) and `sso` (Dex `groups` claim value → teams; the Dex scope
`groups` is requested, the upstream connector must emit it) are best-effort and
additive: a team absent from LiteLLM is skipped (log `login: team does not
exist`) and retried at the next login, a LiteLLM error never blocks the login, a
removed mapping never detaches. LiteLLM is the source of truth — ACH never
creates these teams. The `ek_`-create fallback that provisions a user LiteLLM does not know uses the same default list. Keys match case-insensitively. Access to an Environment
follows at its next reconcile (the operator attaches the user's shell team).
`ach-cli refresh` → `POST /platform/refresh` (pk_ only, else 401
`invalid_key_type`) re-runs the `users`/`sso` enrolment on demand without a
browser: it replays the user's shared Dex refresh token (the same IdP
revalidation as `/token`; refused = 401 `ach_login_required`, Dex down = 503
`idp_unreachable`) and reads `groups` from the refreshed id_token (the Google
connector re-reads the Directory API on refresh); 204. The `/token` refresh and
console revalidation never enrol, by design: the per-team LiteLLM lookups stay
off the hourly path.

<drift_callouts>
**Drift flag #4 — final resolution:** The operator Pod has TWO metric endpoints (operator:8080, CS:8082). A Pod-level scrape annotation can name only one port. Decision: **annotate the Pod for the operator port (:8080)** and **annotate the `ach-content-service` Service for the CS port (:8082)**. Prometheus's default kubernetes-pods scrape role discovers Pod annotations; the kubernetes-services scrape role discovers Service annotations — both are scraped, both produce metrics. The Prometheus Operator's ServiceMonitor example we ship as `examples/prometheus-servicemonitor.yaml` is an alternative for users who don't run the default scrape config.

**Why not split the operator Pod?** RWO PVC constraint (CLAUDE.md "Repository-specific patterns"): the operator writes to the cache PVC and the content-service reads from it; RWO mandates single-Pod co-location.

**Why not relabel_configs?** Default Prometheus scrape configs use port-from-annotation. Relabel-based per-container scraping requires a custom Prometheus config that not every deployer has. Annotating the Service is the lower-surprise default; ServiceMonitor is the higher-surface opt-in.

**RBAC note (no edit needed):** Per CONTEXT spec v4 §5.2 reversal: "Content Service ServiceAccount drops `get/list/watch` on ACH CRDs". BUT the operator Pod hosts the CS container; both containers share the `ach-operator` ServiceAccount. The operator SA MUST keep CRD read perms for its own reconciler informers (Phase 1 Plan 01-09 grants them). The §5.2 RBAC contract is therefore enforced at the GO CODE LEVEL by Plan 05-06 removing the manager.Manager from `cmd/ach/cmd/content_service.go`; the SA-level enforcement is not applicable in the co-located-Pod topology. This plan documents that fact in the chart with a comment.
</drift_callouts>
</context>

<objective>
Close WR-02 (data integrity for credential-bearing files): all four adapter `copyFile` helpers (claudecode:327, codex:457, gemini:547, opencode:408) use the pattern `defer func() { _ = out.Close() }()` for the destination file. On Linux with buffered I/O, `close(2)` can return EIO when the final kernel-buffer-to-disk flush fails (disk full, ECC error, network FS hangup, mount disappeared). The current pattern silently swallows that error: the caller sees `copyFile` return nil, records the file as successfully written, hashes the partial output, writes a state.json entry, and reports success — but the file on disk is missing its last buffered bytes.

For credential-bearing files (the adapter output is run through stage.go which feeds WriteAtomic, but the same adapters' `copyFile` is also used for content artifacts via the plugin .mcp.json contribution path), a truncated tail can corrupt the JSON/TOML structure, making the runtime config silently invalid on next AI-agent startup. The user discovers "claude-code can't find any tools" hours later with no log trace pointing back to the write failure.

The fix is mechanical and identical across all four adapters: replace `defer func() { _ = out.Close() }()` with an explicit `out.Close()` at the success path, returning its error.

This plan does:

1. In each adapter's `copyFile`, replace the deferred-close pattern with the canonical Go idiom from `code review feedback recommendation`:

   - Keep `defer in.Close()` for the source (read-only — close errors here are immaterial).
   - On the destination, remove `defer out.Close()`. Instead: after a successful `io.Copy`, return `out.Close()`. On `io.Copy` error, call `out.Close()` (ignoring its error) and return the io.Copy error.

2. Add a unit test per adapter (`TestCopyFile_SurfacesCloseError`) that uses a small testing technique to induce a close-time error. Two viable approaches:

   - (a) **TempDir + readonly mode**: write a destination file, chmod the parent dir to readonly, then attempt to rename — but rename isn't in copyFile, so this doesn't apply.
   - (b) **Interface seam**: introduce a package-private `osCreate = os.OpenFile` function variable that tests can override with a fake returning an `os.File` whose Close fails. Simplest; matches existing test-seam patterns in the codebase.
   - (c) **Mock via interface**: refactor copyFile to take an `io.WriteCloser` factory. More invasive.

   Pick (b). Add a package-level `var openDst = os.OpenFile` (a function variable with the same signature). In production this is `os.OpenFile`; in tests, override via `openDst = func(name string, flag int, perm os.FileMode) (*os.File, error) { return f, nil }` where `f` is a fake file. The test seam approach is consistent with how the codebase already structures hot-swap injection (manifestFetcher in commit.go, killFn in commit.go).

   Wait — `*os.File.Close()` can't be mocked because it's a struct method. Reconsider: the test seam needs to return an `io.WriteCloser`, not `*os.File`. This requires copyFile's local `out` variable to be typed `io.WriteCloser`, not `*os.File`. That's fine for `io.Copy(out, in)` (io.Copy takes io.Writer) but requires the test seam to swap the function entirely. Cleanest: copyFile remains pure (no seam), but the test uses real OS behavior to induce a close-error — e.g., by writing to a file on a tmpfs that gets unmounted, or by closing the underlying fd via syscall before the deferred close fires. Both are platform-specific and flaky.

   Final decision: use approach (b) but parameterized differently. Introduce a private function `copyFileImpl(src, dst string, openDst func(string, int, os.FileMode) (*os.File, error)) error` and a wrapper `copyFile(src, dst string) error { return copyFileImpl(src, dst, os.OpenFile) }`. Tests call `copyFileImpl` directly with a fake `openDst` that returns an `*os.File` opened on a small tmpfile then closed via os.Close BEFORE returning — so the subsequent operations on it hit "file already closed" semantics. Verify this produces an io.Copy error or close error reliably; if not, fall back to a test on the public copyFile with a destination directory that doesn't exist (causing open to fail, exercising a different return path but proving the deferred-close-no-longer-swallows contract).

   Simpler alternative for the tests: induce a close error by writing to `/dev/full` (Linux). Writing to /dev/full succeeds (the writer accepts bytes) but close() returns ENOSPC. This is the canonical Go-testing approach for buffered-write-then-fail-on-close scenarios. ONLY works on Linux — guard the test with a runtime.GOOS == "linux" skip.

   Use the /dev/full approach. It tests real OS semantics, no test seam needed, no copyFileImpl factoring required. Skip on non-Linux. Add a test helper `requireLinux(t *testing.T)` to each adapter's test file (or share via a single package).

3. Update each adapter's existing copyFile-related test (if any) to confirm the behavior is preserved on the success path.

Output: 4 source files (one copyFile per adapter, identical mechanical edit) + 4 test files (one test per adapter, near-identical fixture). ~30 LOC net per adapter (replace defer block + new test). No new dependencies.

Purpose: data integrity for adapter outputs. Once the engine actually writes adapter configs (W5-01 closes CR-02), this fix ensures that "write succeeded" means "bytes are durably on disk" — not "bytes were buffered and the close failure was silently dropped."
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| io.Copy → os.File buffer | Bytes accepted by io.Copy go into the kernel's write buffer; the buffer is not flushed to disk until close() or fsync(). |
| os.File buffer → disk | Final flush at close() can fail with EIO/ENOSPC; if the error is dropped, the file appears written but is truncated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-W5-05-01 | Information Disclosure / Data Loss | adapter.copyFile destination close error | mitigate | Replace `defer func() { _ = out.Close() }()` with explicit `return out.Close()` so EIO/ENOSPC propagates to the caller; caller sees the error and aborts the hydrate (no partial state.json entry recorded for a truncated file). |
| T-07-W5-05-02 | Tampering | partial credential file written then truncated by close failure | mitigate | Same — the explicit close error means the caller never records the file as written, so the state.json never carries a hash for the truncated bytes. The atomic-rename pattern in stage.go (called separately by the extract path) is unaffected by this fix; copyFile is the inner-loop helper for plugin-contributed file copies. |
| T-07-W5-05-03 | Denial of Service | repeated EIO on /dev/full or full disk | accept | The fix surfaces the error; the caller exits non-zero. This is the correct outcome — a hydrate cannot succeed when the disk is full. The runtime gate is the user (or CI) to free disk space. |
</threat_model>

### `internal/litellm/keyinfo.go` (Go source, LiteLLM pass-through fetcher) — MODIFY

**Analog:** itself. The function shape stays identical; ONLY the path string and the response decoder change.

**Current code to replicate the shape of** (lines 39–62):
```go
// ListUserKeys issues GET /key/info?user_id=<userID> and returns the
// LiteLLM keys owned by a specific user. Used by the Plan 08 orphan-
// cleanup Runnable (D-16) to enumerate all keys associated with an
// ACH-managed LiteLLM user; the caller cross-references the returned
// set against active personal_keys / environment_keys rows per Hub
// §18.4 to identify orphans.
//
// Empty result is NOT ErrNotFound — a user may legitimately have zero
// keys (e.g. their pk_ was just revoked and there is no ek_ for them).
// Callers decide whether absence is interesting.
//
// §9.1: only the user_id and status code are logged — no response body.
func (c *RESTClient) ListUserKeys(ctx context.Context, userID string) ([]UserKeyInfo, error) {
    path := "/key/info?user_id=" + url.QueryEscape(userID)
    raw, err := c.makeRequest(ctx, "GET", path, nil)
    if err != nil {
        return nil, err
    }
    var resp ListUserKeysResponse
    if err := json.Unmarshal(raw, &resp); err != nil {
        return nil, fmt.Errorf("litellm: decode GET /key/info: %w", err)
    }
    return resp.Keys, nil
}
```

**What the planner must change:**
- Path string: `"/key/info?user_id=" + url.QueryEscape(userID)` → `"/key/list?user_id=" + url.QueryEscape(userID) + "&return_full_object=true&include_team_keys=false"`
- Error wrap message: `"litellm: decode GET /key/info: %w"` → `"litellm: decode GET /key/list: %w"`

**What the planner must PRESERVE (load-bearing):**
- Function signature (Client interface contract, unchanged per D-03 / context line 83).
- The `§9.1` no-response-body-logging comment at line 50 — this is the [feedback_litellm_operator_no_redaction_filter] discipline. The new decode path MUST NOT log the token either.
- The "empty result is NOT ErrNotFound" semantics — caller (orphan loop) treats empty as legitimate.
- Use of `url.QueryEscape` for the user_id (XSS / param-injection defense).
- Error-propagation shape: `makeRequest` errors propagate verbatim; only the decode-error wrap mentions the path.

**Pass-through discipline reminder** (project memory `feedback_litellm_operator_pass_through`): the new path string is constructed without policy / version-gating. Boolean query params (`return_full_object=true&include_team_keys=false`) are LiteLLM-side semantics — ACH passes them verbatim, does not validate the response against them.

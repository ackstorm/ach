Three plans, scoped from `.planning/ROADMAP.md` Phase 02.2 entry and `.planning/phases/02.1-.../02.1-01-SUMMARY.md` "Follow-up items for Phase 02.2 / future":

1. **Plan 1 — Fix Gap G1 (`ListUserKeys` endpoint mismatch).** `internal/litellm/keyinfo.go:51` calls `/key/info?user_id=...` which LiteLLM v1.83.10 returns `404 not_found_error "Key not found in database"` for; that endpoint looks up a SPECIFIC key by `?key=<token>`, not by user. The correct endpoint is `/key/list?user_id=...&return_full_object=true&include_team_keys=false`. The response `token` field is the LiteLLM-internal opaque hex key id (NOT ACH's `pkid_*`/`ekid_*` prefix), so the orphan loop's set-difference key must change. Resolution requires three coupled changes: swap endpoint, update `UserKeyInfo` / `ListUserKeysResponse` structs, and add the namespace-translation column.

2. **Plan 2 — LiteLLM-real UAT path via docker-compose.** Merge the spike-only LiteLLM services into root `docker-compose.yml` behind a `profiles: [litellm]` gate (off by default), retire `docker-compose.spike.yaml`, update `scripts/uat-sc5.sh` to drop its `-f docker-compose.spike.yaml` arg, and author `scripts/uat-g1.sh` that mirrors `uat-sc5.sh --full` (backdate + grep) to exercise the G1 revocation path against a live LiteLLM v1.83.10.

3. **Plan 3 — Docs update for invariant relaxations.** Phase 02.1 permanently lifted two Phase 02 invariants. Edit T-02-02-03 entries in-place across the Phase 02 plan/SUMMARY/REVIEW/VERIFICATION docs to read `LIFTED 2026-05-18 (Phase 02.1 commit 45b7558)`, qualify the CLAUDE.md `HTTPS-only` security bullet so it scopes to Platform API ingress only (NOT upstream `HTTPSource`), add a CLAUDE.md note that SCM `authSecretRef` is optional (Phase 02.1 commit `94f24b5`), and append two rows to PROJECT.md `Key Decisions` table (one per relaxation, `Outcome: Lifted Phase 02.1`).

## Implementation Decisions

### Plan 1 — G1 namespace fix shape

- **D-01:** **DB column path (migration 000003).** Add a nullable `litellm_token TEXT` column to both `personal_keys` and `environment_keys`. Migration sequence is 000003 (Phase 02 added 000002). The orphan loop's set-difference key changes from `litellm_user_id` (existing) to `litellm_token` (new). Adapter-map (in-memory token→user_id reconstruction per tick) was considered and rejected — the DB column aligns with the §18.4 spec wording (cross-reference by stable identifier) and keeps the orphan-detection logic as a DB set-difference rather than per-tick reconstruction. Greenfield: no backfill needed; nullable so unwritten rows are silently skipped by the orphan loop until Phase 3 SSO populates them.
- **D-02:** **Phase 3 SSO is the documented write path for `litellm_token`.** Plan 1 ships the schema + reader-side change only. The orphan loop iterates over rows where BOTH `litellm_user_id` AND `litellm_token` are non-null (fully-linked rows). Phase 3's SSO write path becomes responsible for populating `litellm_token` on `/key/generate` — this is captured as a downstream prerequisite in Plan 1's `Out of scope` section and as a sentence in the Phase 3 context when that phase arrives.
- **D-03:** **Wire-format validation lives in Plan 2 only — real LiteLLM is the wire oracle.** Plan 1 updates the endpoint string + struct shape; it does NOT add a `httptest.Server`-based unit test in `internal/litellm/keyinfo_test.go`. The fake-server approach was considered and rejected because Plan 2's `scripts/uat-g1.sh` hits a real LiteLLM v1.83.10 end-to-end and is the load-bearing wire-format check. A fake server would duplicate that signal and could drift from upstream silently. Plan 1's struct/endpoint changes can rely on mocked `litellm.Client` unit tests for orphan-loop logic + Plan 2 for wire format.

### Plan 2 — LiteLLM compose shape

- **D-04:** **Merge LiteLLM services into root `docker-compose.yml` behind `profiles: [litellm]`.** Both new services (`litellm` + `litellm-db`) carry `profiles: ["litellm"]`. `make dev-up` (no profile) brings up only the existing `postgres` + `redis` services for day-to-day Phase 1+ work. `docker compose --profile litellm up -d` or `docker compose -f docker-compose.yml --profile litellm up -d` adds LiteLLM. Aligns with [[feedback_local_uat_docker_compose]] (extend root compose; UAT-runner-style invocation).
- **D-05:** **Retire `docker-compose.spike.yaml` outright.** Delete the file in Plan 2. `scripts/uat-sc5.sh` is updated to (a) drop its `-f docker-compose.spike.yaml` arg from the `COMPOSE` variable and (b) add `--profile litellm` to its `$COMPOSE up -d` invocation. One source of truth (root `docker-compose.yml`) for all compose services going forward. The `--profile litellm` gate keeps the day-to-day-dev footprint unchanged.
- **D-06:** **LiteLLM image pin stays `ghcr.io/berriai/litellm-database:v1.83.10-stable`** — verbatim from `docker-compose.spike.yaml` per [[feedback_litellm_version_control]]: no version-probe / version-gate logic, engineer picks the version manually. The 1.83.10 pin is load-bearing because earlier versions have the Prisma defect that prevents MCP CRDs from being created.
- **D-07:** **Separate LiteLLM Postgres (`litellm-db` service)** — LiteLLM's Prisma auto-schema collides with ACH's `golang-migrate` schema on shared table names. Mirrors `docker-compose.spike.yaml` rationale verbatim. Both Postgres containers stay `postgres:16-alpine` per Phase 02.1 D-04 / Phase 1 docker-compose.yml.
- **D-08:** **`spike-litellm-config.yaml` stays at `scripts/spike-litellm-config.yaml`** — the path is referenced by the merged compose service (`volumes: ./scripts/spike-litellm-config.yaml:/app/config.yaml:ro`). Rename to `scripts/litellm-config.yaml` (drop the `spike-` prefix) since the spike concept is being retired — captured in Plan 2 task list. `LITELLM_SPIKE_PORT` env var likewise renames to `LITELLM_PORT` (default `14000` preserved).

- `uat-g1.sh` audit-event grep pattern: `grep -E '"audit":true.*"outcome":"revoked".*"user_id":"u-uat-g1"' "$OPERATOR_LOG"` (JSON form — operator emitter is `slog.NewJSONHandler`; the key=value form was a wire-format note error caught post-checker on 2026-05-18) — exact prefix `u-uat-g1` keeps it disambiguated from any other test runs sharing the LiteLLM DB.

- The migration's `litellm_token` column constraint: `NULL` allowed (Phase 3 SSO populates later), `UNIQUE` index — LiteLLM tokens are globally unique within a LiteLLM instance, so the constraint is correct. CHECK constraint NOT applied (Phase 1 chose `pkid_*`/`ekid_*` CHECK on `key_id` but the LiteLLM-internal hex token has no fixed prefix).

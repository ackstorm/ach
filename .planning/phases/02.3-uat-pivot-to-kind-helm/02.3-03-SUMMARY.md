## Bug found and fixed during live run

`make e2e-focus FOCUS=TestPhase2SC5Orphan` exited 1 on first run:
- `IntervalFloor` PASS (16.22s)
- `OrphanReapLive` FAIL (12.15s) — empty audit buffer

Root cause: `backdateLiteLLMKey` used `WHERE token = $plaintext` against `LiteLLM_VerificationToken`. LiteLLM's `/key/generate` returns the plaintext key in `.key` but the DB `token` column stores the SHA-256 hash. The plaintext-against-hash match returned 0 rows; the orphan key kept its current `created_at`; the orphan loop's `if !k.CreatedAt.Before(cutoff)` check skipped it; no audit event emitted.

Fix: renamed `backdateLiteLLMKey` → `backdateLiteLLMKeyByUser`. Switched the WHERE clause to `WHERE user_id = $userID` and added a `tag.RowsAffected() == 0` guard so a silently-empty UPDATE fails the test loudly. Matches the proven pattern from the deleted `scripts/uat-sc5.sh` (`WHERE user_id = 'u-uat'`).

Re-run after fix: both sub-T PASS (28.05s total).

Captured audit event (the assertion target):
```json
{"time":"2026-05-20T20:23:49.524113121Z","level":"INFO","msg":"operator.orphan-cleanup","audit":true,"target.kind":"litellm_key","target.name":"6d041162e1bc5dddf0144fc1bfb9781661eeffaae989816631bd8642a09ac11f","outcome":"revoked","user_id":"u-e2e-sc5"}
```

All three assertion fields present: `"audit":true`, `"outcome":"revoked"`, `"user_id":"u-e2e-sc5"`. `target.name` carries the LiteLLM-side hashed token, confirming the orphan-reap loop revoked the key it generated under that user.
